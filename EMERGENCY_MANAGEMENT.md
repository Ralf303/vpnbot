# Аварийное управление зарубежными выходами

Реализовано 9 сентября 2026. Московский сервер остаётся точкой входа OpenVPN,
хранилищем PKI, PostgreSQL и местом запуска обоих адаптеров бота. Зарубежные
серверы обеспечивают WireGuard/NAT и, по выбору, приватный SOCKS для Telegram.
Смена страны не меняет адрес подключения, сертификат, файл или срок подписки.

## Сценарии в боте

В Telegram пункт **Серверы** открывает прежние карточки OpenVPN-серверов:
добавление, переименование и статистику. **Аварийное управление** — отдельный
пункт для зарубежных выходов; он не заменяет обычное управление серверами.

### Смена страны пользователем

В Telegram или VK: **Мои конфиги → конфиг → Сменить сервер → выход**.
Бот проверяет новый выход и меняет назначение сертификата в Москве.
Выбор применяется к текущему подключению и сохраняется после переподключения.
Существующие TCP-соединения могут оборваться при смене публичного IP;
иногда требуется переподключить VPN. Новый `.ovpn` не нужен.
Российские назначения по-прежнему идут через Москву.

### Старый выход недоступен, резерв уже готов

В личном чате VK отправить `/admin`, `админ` или `авария`, либо открыть
кнопку **Аварийное управление**. В Telegram эта кнопка находится в админ-панели.

1. Открыть старый выход → **Переключить всех с этого выхода**.
2. Выбрать готовый резерв.
3. Подтвердить **Переключить VPN** либо **VPN + Telegram**.

Для второго варианта резерв должен поддерживать Telegram. Проверяются канал,
внешний адрес/NAT и, при переключении Telegram, доступность его API через SOCKS.
Старый выход не опрашивается. Меняются назначения подключённых и отключённых
пользователей; если старый выход был основным, новые конфиги тоже используют резерв.
Выбор пользователей других выходов сохраняется. Отчёт считает действующие
управляемые конфиги; старые сохранённые назначения переносятся также.

### Единственный выход сломан, нужно добавить новый VPS

1. Открыть аварийное управление VK → **Добавить VPS**.
2. Выбрать **VPN + доступ Telegram** или **Только VPN**.
3. Отправить четыре строки: публичный IPv4, SSH-порт, пароль root, название.
   Этот порядок одинаков в Telegram и VK. Для другого пользователя с sudo
   поддерживается прежний формат: название, IPv4, порт, логин, пароль.
4. Открывать **Статус установки**, пока не завершатся проверки.
5. Выполнить перенос со старого выхода по предыдущему сценарию.

Требуется чистый Ubuntu/Debian, root либо пользователь с sudo, доступ к пакетным
репозиториям, SSH из Москвы и UDP между серверами. Новый VPS должен иметь прямой
публичный IPv4, совпадающий с внешним адресом NAT. Установщик не заменяет чужой
WireGuard или Dante. При ошибке нужно исправить причину и добавить тот же адрес
повторно; установка продолжится с прежним идентификатором и проверкой SSH-ключа.

Режим Telegram устанавливает приватный SOCKS, а сам бот остаётся в Москве.
Второй процесс с тем же Telegram-токеном не запускается. Прокси можно переключить
отдельно кнопкой **Использовать для Telegram**, без изменения VPN пользователей.
Установка продолжается в фоне на Москве, даже если чат закрылся. Отключение
самой Москвы выходит за границы этого сценария.

Неудачные обычные OpenVPN-установки видны в «Серверах». Если управляющий ключ
ещё не был получен, повторное добавление того же адреса продолжает настройку
той же записи и сохраняет relay-порт. Действующий сервер или текущая установка
повторно не запускаются. Пять строк в обычной четырёхстрочной форме отклоняются
целиком, чтобы логин/пароль не сместились в другие поля.

## Доступ и секреты

- `VPN_ENTRY_SERVER_KEY` — ключ существующего московского OpenVPN-сервера в БД.
  Его нельзя удалять старой кнопкой управления серверами при включённом менеджере.
- `ADMIN_VK_ID` — подтверждённый цифровой VK ID администратора. Он позволяет
  войти без новой привязки через Telegram. Также признаётся уже связанный
  аккаунт администратора `ADMIN_TELEGRAM_ID`.
- Каждое административное событие проверяет отправителя и личный чат.
  Пользователь может переключать только свои действующие конфиги.
- SSH-пароль передаётся установщику через stdin и остаётся только в памяти
  процесса. Он не попадает в реестр, argv или журналы бота. Само сообщение
  остаётся в истории мессенджера; автоматическое удаление не реализовано.
- Управляющий SSH бот → Москва всегда прямой, с проверкой сохранённого
  fingerprint. Новый VPS использует первое SSH-подключение для регистрации
  ключа; при повторной установке смена ключа блокирует продолжение.
- Пользователю `vpn-bot` разрешён только root-helper без аргументов; команды
  передаются ограниченным JSON. Произвольного root shell у бота нет.

## Серверная реализация

`EgressService` и общий `EgressAdmin` обслуживают Telegram и VK. Цикл запуска
Telegram повторяет подключение независимо от VK; недоступный Telegram не
задерживает запуск VK после перезапуска контейнера.

Иностранные выходы не являются новыми `VpnServer` в PostgreSQL. Сертификат
продолжает принадлежать московскому серверу. Реестр root находится в
`/etc/vpnbot-egress-manager/state.json`: выходы, основной выход, прокси,
назначения `Common Name → exit ID`, номер ревизии и ход установки.
Схема БД не меняется. Старые кнопки перевыпуска управляемых конфигов тоже
переходят к смене выхода, чтобы случайно не отозвать сертификат.

| Компонент | Назначение |
| --- | --- |
| `vpnbot-egress-control` | JSON API, установка VPS, проверки, смена маршрутов |
| `vpnbot-egress-manager.service` | Восстановление маршрутов при загрузке |
| `vpnbot-egress-events.service` | Локальный Unix socket событий OpenVPN |
| `vpnbot-egress-map.timer` | Сверка CN/IP по status-version 3 каждые 2 секунды |
| `vpnbot-egress-hook` | Сохраняет старые hooks и вызывает обработчик маршрута |
| `vpnbot-egress-session` | Отправляет CN/IP при подключении и отключении |

OpenVPN hooks работают без sudo. Root-демон проверяет `SO_PEERCRED`, принимает
только root и пользователя OpenVPN, проверяет CN/IP и обновляет nftables до
завершения client-connect. Существующий client-disconnect учёта трафика
сохраняется в цепочке. Systemd ждёт готовности Unix socket перед запуском OpenVPN.

После GeoIP-классификации (mark `0x210` только для зарубежных назначений)
nftables `inet vpnbot_exits` назначает марку выхода по внутреннему IP клиента.
Для `eN` используются таблица/марка `23000+N`, правило `12000+N`, WG-интерфейс
и постоянный резервный blackhole. Российские и служебные назначения не меняются.
Карта nftables заменяется одной транзакцией. Реестр защищён блокировкой, запись
атомарна; подтверждение со старой ревизией отклоняется.

Действующий DE принят как `e1` с интерфейсом `wg-de`. Новые выходы используют
`wgeN`, подсеть `10.214.N.0/30`, UDP `53000+N` на RU и `51822` на VPS,
MTU 1400, MSS 1360, keepalive 15 секунд. Ключи независимы для каждого канала.
Зарубежный SOCKS слушает только адрес WireGuard и допускает только peer Москвы.

При отказе назначенного выхода зарубежный трафик остаётся на нём/blackhole,
пока администратор не выберет резерв. Автоматического переноса между странами
нет. Старый healthcheck table 210 остаётся для трафика без назначения и основного
маршрута; его fallback через RU не означает fallback управляемых соединений.

## Установка серверной части на существующую Москву

Предусловия: действующая схема из `NETWORK_FAILOVER_2026-09-09.md`, OpenVPN
`server-tcp`/`tun1`/`10.9.0.0/24`, WG-выход, root, Python 3, nftables,
iptables, iproute2, curl, sudo, WireGuard и `python3-paramiko`. Службы
`vpnbot-route-health` и `vpnbot-bot-proxy.socket/service` уже должны быть настроены.
Первый установщик специально принимает действующий выход, а не строит Москву с нуля.

```bash
apt-get install -y python3-paramiko
python3 deploy/install-egress-manager.py --entry-host RU_PUBLIC_IP --name 'Действующий выход' --telegram
# Проверить результат и затем активировать hooks: один перезапуск OpenVPN.
python3 deploy/install-egress-manager.py --entry-host RU_PUBLIC_IP --telegram --activate-hooks
```

Установщик сохраняет предыдущие файлы в `/root/vpnbot-backups/emergency-control-*`.
Для эксплуатации выставить `VPN_ENTRY_SERVER_KEY` и `ADMIN_VK_ID` в серверном
`.env`, собрать образ и пересоздать только контейнер бота. PostgreSQL не удалять.

Проверки:

```bash
printf '{"action":"status"}' | sudo -u vpn-bot sudo -n /usr/local/sbin/vpnbot-egress-control
printf '{"action":"check","id":"e1"}' | /usr/local/sbin/vpnbot-egress-control
systemctl status vpnbot-egress-events vpnbot-egress-map.timer openvpn-server@server-tcp
nft list table inet vpnbot_exits
ip -4 rule show
ip -4 route show table 23001
journalctl -u vpnbot-egress-events -u vpnbot-egress-map --since '-10 min'
```

Статус `ready` означает успешную установку, а не непрерывную проверку здоровья.
Кнопка **Проверить** выполняет свежую проверку; перед каждой сменой назначения
она запускается автоматически. При неудаче новый маршрут не выбирается.

Диагностика 10 сентября после переустановки FI: пароль root подтвердился при
SSH через DE, но прямые TCP/22, TCP/40022 и UDP/51822 из RU до FI не дошли
(проверялся также захват пакетов на FI). Обратный UDP FI:51822 → RU:53002
тоже не прошёл; ICMP из FI в RU работал. Проверенные локальные firewall не
блокировали эти подключения. Требуется проверка внешней фильтрации/маршрута
между VPS; точная сторона отказа не установлена. VPN на FI при диагностике
не устанавливался. Повторная установка ОС сама по себе связность не гарантирует.

## Резервные копии и откат

Вместе с PostgreSQL, PKI и `.env` сохранять `/etc/vpnbot-egress-manager`,
`/etc/wireguard`, systemd drop-ins, sudoers и исходные hooks OpenVPN.
Реестр содержит назначения пользователей, а каталог WireGuard — приватные ключи;
эти файлы нельзя помещать в публичный Git.

При откате приложения старый образ можно запустить без удаления реестра и
маршрутов: пользовательские файлы от этого не меняются. Для полного отката
серверной части сначала восстановить прежний OpenVPN config и убрать его
drop-in `egress.conf`, затем перезапустить OpenVPN. После этого остановить
таймер/демон менеджера, убрать только таблицу `inet vpnbot_exits` и его policy
rules, восстановить сохранённый `/etc/default/vpnbot-routing` и выполнить
`vpnbot-route-health`. Не очищать весь nftables и не отзывать сертификаты.
Если уже добавлены новые выходы или изменены назначения, сначала выбрать
работающий основной маршрут для всех пользователей и сохранить актуальный реестр.

## Проверки разработки и пределы приёмки

TypeScript-тесты проверяют авторизацию VK, владение конфигом, прямой SSH,
ошибки без секретов, подтверждения и независимый перезапуск Telegram.
Python-тесты проверяют перенос с мёртвого источника, откат, ревизии,
сохранение назначений и генерацию shell для обоих режимов установки.

```bash
npm run typecheck
npm test  # с отдельной тестовой PostgreSQL, см. README
python3 tests/egress-control.test.py
sudo unshare --net python3 tests/egress-netns.test.py
```

Последняя проверка использует настоящие nftables и policy routes в изолированном
сетевом пространстве, включая смену IP после reconnect и blackhole при отказе.
Существующий DE принят и проверен на рабочей Москве. Развёртывание через новую
форму на втором чистом VPS требует отдельной приёмки, когда такой VPS будет
предоставлен; действующий DE ради этой проверки не переустанавливается.
