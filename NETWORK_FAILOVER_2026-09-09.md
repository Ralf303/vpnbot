# Замена финского выхода резервом в Германии — 9 сентября 2026

Дополнение: после этого восстановления установлен менеджер выходов, описанный
в [EMERGENCY_MANAGEMENT.md](EMERGENCY_MANAGEMENT.md). Германия зарегистрирована
как `e1`; подключённые клиенты получают mark/table `23001`. Table 210 остаётся
для немаркированных менеджером соединений. Автоматический fallback через RU
из исторического описания ниже не применяется к назначенным выходам клиентов.

## Причина и действующая схема

После восстановления 8 сентября SSH TUN `tun99` многократно разрывался с
`peer ignored channel window`; часть переподключений завершалась тайм-аутом.
Короткий первоначальный замер скорости не выявил нестабильность длительной работы.

9 сентября в 20:58–21:02 МСК публичный адрес FI перестал отвечать на ICMP и SSH
из RU, с компьютера администратора и из зарубежного сервера-примера. Из последнего
ICMP к контрольному внешнему адресу проходил без потерь. Внутри `tun99` — 100%
потерь; healthcheck удалил финскую policy route. Это отдельный инцидент
доступности FI: отличить зависание VPS от отказа сети перед ним без консоли
провайдера невозможно. Серверы-примеры проверялись только чтением.

По запросу администратора подготовлен чистый резерв DE на Ubuntu 24.04.
Прямой UDP между RU и DE работает, поэтому выбран WireGuard, без SSH TUN.

```text
Телефон со старым .ovpn → RU TCP/443 → OpenVPN tun1, 10.9.0.0/24
                                      ├─ российские IPv4 → NAT RU
                                      └─ прочее → mark 0x210, table 210
                                                   ↓
                                           WireGuard wg-de
                                           10.212.0.1 ↔ 10.212.0.2
                                                   ↓
                                                NAT DE
```

OpenVPN endpoint, PKI, бот, PostgreSQL и пользовательские профили остаются на RU.
Перенос сертификатов на DE и изменение файлов на телефонах не нужны.
Сервер `srv_1` в боте переименован в «Германия 🇩🇪», его SSH host и ключ не менялись.
Все 92 записи конфигов до и после переключения дали одинаковый SHA-256;
84 активных конфига успешно скачаны через `ConfigService`, каждый указывает на
прежний RU endpoint TCP/443. Сроки действия, владельцы и сертификаты сохранены.

## Конфигурация

На обоих серверах:

- `/etc/wireguard/wg-de.conf`, права 0600, независимые ключи, UDP/51822;
- `wg-quick@wg-de.service` включён при загрузке;
- MTU 1400, `Table = off`, keepalive 15 секунд;
- `PostUp` устанавливает `net.ipv4.conf.wg-de.rp_filter=2`;
- `/etc/default/vpnbot-routing` из `deploy/vpnbot-routing-germany.defaults`.

Шаблоны: `deploy/wg-de-ru.conf.example` и `deploy/wg-de-egress.conf.example`.
Заполнители публичных адресов и ключей заменяются только на сервере. Приватные
ключи генерируются с `umask 077` и не переносятся через Git.

На RU peer DE имеет `AllowedIPs = 0.0.0.0/0`, но `Table = off` предотвращает
изменение основного маршрута сервера. Только маркированный трафик направляется
через table 210. Параметры выбора: интерфейс `wg-de`, peer `10.212.0.2`, MSS 1360.
В FORWARD добавлены два MSS-правила для `tun1 ↔ wg-de` штатным форматом скрипта
`vpnbot-moscow-routing`. GeoIP-набор и российский NAT сохранены.

Drop-in `vpnbot-moscow-routing.service.d/transit.conf` заменён содержимым
`deploy/vpnbot-moscow-routing-wireguard.conf`. Drop-in
`vpnbot-route-health.service.d/germany.conf` из
`deploy/vpnbot-route-health-wireguard.conf` добавляет `After` и `Wants` для
`wg-quick@wg-de.service`. Healthcheck продолжает проверять peer каждые 10 секунд.
При потере канала он возвращает московский выход; существующие соединения могут
прерваться из-за смены внешнего IP, а доступность зарубежных сайтов через RU
не гарантируется.

На DE peer RU разрешены только `10.212.0.1/32` и `10.9.0.0/24`.
Установлены `deploy/vpnbot-egress` и `deploy/vpnbot-egress.service`:

- возвратный маршрут `10.9.0.0/24 dev wg-de`;
- forwarding клиентской подсети и обратных established/related соединений;
- MASQUERADE клиентской подсети через `ens3`;
- постоянный `net.ipv4.ip_forward=1` в `/etc/sysctl.d/90-vpnbot-egress.conf`;
- зависимость и совместный перезапуск egress-службы с `wg-quick@wg-de`.

Скрипт добавляет только отсутствующие правила с комментарием `vpnbot-egress`;
повторный `up` не дублирует их, `down` удаляет только собственные правила.

Дополнительно восстановлен внутренний SOCKS для бота. При подготовке рассылки
проверка `getMe` выявила `ECONNREFUSED` на настроенном в контейнере порту 1081:
там отсутствовал listener. Прежний SSH listener на 1080 не соответствовал
настройке приложения. Теперь путь управления не зависит от FI:

```text
Telegram/управляющий SSH из контейнера
 → RU Docker gateway:1081 (vpnbot-bot-proxy.socket/service)
 → 10.212.0.2:1080 по WireGuard
 → Dante на DE → внешний сервис
```

На DE установлен `dante-server` с `deploy/danted-vpnbot.conf` и drop-in
`deploy/danted-wireguard.conf`. Он слушает только `10.212.0.2:1080`, разрешает
TCP CONNECT только от `10.212.0.1/32`; публичного SOCKS listener нет.
На RU установлены `deploy/vpnbot-bot-proxy.socket` и `.service`: listener
привязан к Docker gateway, а `FreeBind=true` позволяет создать его до Docker
без цикла зависимостей `sockets.target` и `docker.service`. Служба соединяется
с DE после поднятия WireGuard. Адреса прокси и токены в окружении бота не менялись.

Старые WireGuard FI и SSH `tun99` не выбраны маршрутизацией. Возвращение FI
в сеть само по себе не переключит пользователей обратно. Сервисы OpenVPN и
бота при переключении не перезапускались.

## Проверки

- WireGuard handshake прошёл в обе стороны и обновлялся в последующих замерах.
- ICMP с IP-размером 1400 байт: 10/10; дополнительные серии 100/100 и 240/240.
- В последней серии RTT 39,8–45,8 мс.
- Передача 64 МиБ внутри нового канала: 280,51 Мбит/с до переключения,
  361,43 Мбит/с при проверке production mark `0x210`.
- HTTPS с источником из OpenVPN-подсети и mark `0x210` показал внешний IP DE
  и `loc=DE`; запрос без mark — RU. Google вернул ожидаемый HTTP 204.
- Тестовый endpoint Cloudflare Speed ответил HTTP 403; это не замер скорости.
  Приведённые числа относятся к межсерверной передаче, а не к скорости телефона.
- Контрольный российский IPv4 входит в действующий nftables-набор `ru4`.
- Проверены скачивание всех активных файлов и неизменность записей конфигов.
- `tests/routing-health.test.py` покрывает default WG, SSH и немецкий WG,
  доступный/недоступный peer, удаление маршрута и повторный запуск без дублей.

Это проверки во время восстановления, а не гарантия многосуточной стабильности.
При повторной жалобе сравнивать публичную доступность DE, `wg show`, потери
внутри канала и table 210; не предполагать автоматически проблему телефона.

```bash
# RU
systemctl is-active openvpn-server@server-tcp wg-quick@wg-de vpnbot-route-health.timer
wg show wg-de
ping -c 10 -M do -s 1372 10.212.0.2
ip -4 rule show
ip -4 route show table 210
ip route get 1.1.1.1 from 10.9.0.1 mark 0x210

# DE
systemctl is-active wg-quick@wg-de vpnbot-egress
ip route show 10.9.0.0/24
iptables -t nat -L POSTROUTING -nv
```

## Резервные копии и восстановление

На RU: `/root/vpnbot-backups/germany-egress-20260909/` содержит исходные
`vpnbot-routing`, `transit.conf`, снимки маршрутов/firewall, проверенный дамп
PostgreSQL и диагностические результаты. Дамп нужен для аварийного восстановления;
для отмены одного переименования сервера восстанавливать всю БД не нужно.

Для восстановления DE установить WireGuard, заполнить шаблон, включить IP
forwarding, установить defaults и egress-скрипт/службу. Включить `wg-quick@wg-de`
и `vpnbot-egress`. Проверить handshake и HTTPS через отдельный тестовый mark/table
до выбора транспорта в `/etc/default/vpnbot-routing` на RU.

Возвращать предыдущий транспорт только после проверки доступности peer и
зарубежного выхода. На RU остановить health timer и его текущий запуск,
восстановить нужные defaults и зависимости, выполнить healthcheck, затем
запустить timer. Не загружать полный старый firewall поверх действующих
Docker-правил. При удалении немецкого выхода сначала переключить пользователей
на проверенный альтернативный маршрут и только затем останавливать `wg-de`.
